# ADR-0008: Pipeline de producción de PR con Codex + sandbox Docker + GitHub (H2)

- **Estado:** Aceptado (GEN-47)
- **Contexto:** H1 (ADR-0006/0007) deja cada issue aprobada en `READY` tras auditar la selección. El roadmap define H2 como: agente de código aislado (Codex) ejecutado en sandbox Docker efímero por issue/run, con preparación de rama, evidencia, commit/push y apertura de PR enlazada a Linear — con idempotencia ante reintentos, fallos parciales, workflows reiniciados y PR/ramas ya existentes, y presupuesto máximo sin duplicados. La ejecución REAL del agente Codex no se incluye en esta issue: los tests usan simulaciones; el adaptador real existe pero exige una imagen sandbox con el CLI de Codex configurada por operaciones.
- **Decisión:**
  - **Puertos application/dominio** (todos reemplazables, tests usan fakes):
    - `planning/ports.py:TaskSpecSource` — resuelve el `ApprovedTaskSpec` humano-aprobado. En H2 se entrega vía **fichero aprobado** (`SF_FACTORY_TASK_SPEC_PATH`, `StaticFileSpecSource`); sin configuración, `UnavailableSpecSource` **falla explícitamente** (`SPEC_SOURCE_UNAVAILABLE`) — nunca se simula aprobación.
    - `process/ports.py:CommandRunner` — única puerta de ejecución de procesos (subprocess en producción; fakes en tests). Los payload travels con `stdin` opcional para prompts largos.
    - `sandbox/ports.py:SandboxRuntime` — runtime efímero aislado. Adaptador real `sandbox/docker.py:DockerSandboxRuntime`: `docker run` efímero por run key (`factory-sandbox-<run_key>`), `--network none`, `--cap-drop ALL`, `no-new-privileges`, rootfs read-only, `/tmp` tmpfs `rw,noexec,nosuid`, CPU/RAM acotados, `--user 1000:1000` (configurable), workspace montado en `/workspace`; bloques de comandos peligrosos **antes** de ejecutar (deny-list pura en `domain/safety.py`: rm -rf en raídes/forza-push git/sudo-su/shutdown/mkfs/dd-of=/dev/chmod 777 raízes/curl|sh/fork bombs/mounts); `run_in_sandbox` vía `docker exec` argv (sin shell); cleanup `docker rm -f` siempre.
    - `agents/ports.py:CodingAgent` — adaptador real `agents/codex_cli.py:CodexCliAgent`: una sesión `codex exec` dentro del sandbox con el prompt transportado por stdin (el guard de seguridad solo escanea argv); mapea el outcome a `AgentRunRecord` (éxito / `AGENT_FAILED` / `AGENT_BLOCKED` si el sandbox rechaza un comando) y limpia el sandbox en todas las rutas. Los fallos técnicos/provisionales (SandboxUnavailable) se propagan para el RetryPolicy de Temporal.
    - `scm/ports.py:GitWorkspaces` + `PullRequestsService` — adaptadores reales `scm/git_cli.py` (clone/checkout -b idempotente por workspace+rama, `status --porcelain` para decidir cambios, `commit` con mensaje convencional, `push` nunca force, `rev-list --count base..HEAD`) y `scm/github_cli.py` (`gh pr list --head` antes de crear; parse de URL). Fallos → `SCMUnavailable` (reintentable).
    - `verification/ports.py:VerificationRunner` — adaptador real `verification/sandbox.py`: re-ejecuta `uv run pytest -q` dentro del sandbox como gate independiente del agente; falla honestamente (`VERIFICATION_FAILED`) o propaga indisponibilidad.
    - `persistence/run_ledger.py:PipelineRunLedger` — libro mayor JSONL append-only idempotente por `run_key` (`GEN-N-vM`), legible entre reinicios: es el **guard de presupuesto** (máximo de runs por issue configurable) y deja traza auditable de cada run preparado.
  - **Extensión del IssueWorkflow (mismo run durable `issue-<GEN-N>`):** con `pipeline_enabled` (settings `SF_FACTORY_PIPELINE_ENABLED`, envía por webhook) la fase `READY` continúa: `PLANNING` (spec + nombres deterministas) → `PREPARING` (presupuesto + workspace/rama) → `IMPLEMENTING` (agente) → `VERIFYING` (gate) → `REVIEWING` (commit/push/PR) → `PR_READY`. Cada transición actualiza el memo y deja UNA línea de auditoría por fase con id sintético `delivery#run_key#FASE` (los reintentos no duplican líneas). Aprobada y **sin** pipeline `→ READY` idéntica a H1.
  - **Errores funcionales vs técnicos:** los contratos de fase (`TaskPlan`, `RunPreparation`, `AgentRunRecord`, `VerificationOutcome`, `PublicationOutcome`) llevan el eje ok/failed **como valor**: `ok=false` termina en `BLOCKED` (razones estables: `SPEC_SOURCE_UNAVAILABLE`, `BUDGET_EXHAUSTED`, `AGENT_FAILED`, `AGENT_BLOCKED`, `VERIFICATION_FAILED`, `CHANGES_EMPTY`, `PUBLISH_FAILED`) con línea de auditoría y memo. Las excepciones (sandbox/scm/proceso inalcanzables) son **técnicas** y las absorben los RetryPolicy por fase (plan 3, prepare 3, agente 2, verify 3, publish 3); si se agotan, el workflow falla y el operador lo reinicia/reset — la re-ejecución es segura: el workspace ya existe, la rama se reutiliza, `find_open` devuelve el PR existente, el ledger no reserva presupuesto dos veces por `run_key`.
  - **Idempotencia de extremo a extremo:** una issue ⇒ una ejecución (`REJECT_DUPLICATE`); un run key ⇒ un presupuesto atómico; una rama determinística `feat/gen-<n>-<slug>` por issue con slugify (acento-insensible, truncada a 48); un PR por head-branch (search-before-create). El humo de integración (`tests/integration/test_pipeline_smoke.py`) prueba todo sobre la stack Temporal real con git local (bare remote) y **sin tokens**.
  - **Secretos:** el sandbox no recibe variables de entorno ni red: ninguna credencial dentro del contenedor. El push/PR se hace en el worker (host) con el transporte configurado del operador (H2: gh CLI configurado externamente). El runbook documenta los límites (imagen con CLI de Codex, deshabilitar `run_as_non_root` si el volume lo exige).
- **Consecuencias:** el workflow de H1 queda extendido pero retro-compatible (el campo nuevo es `False` por defecto y los tests de H1 siguen en verde). La planificación humana real (extraer criterios de Linear vía API) llega con H3+; hoy el fichero aprobado es el puente operacional. El presupuesto por issue es finito por diseño; reintentos Técnicos no duplican trabajo gracias a idempotencia de las activities.
