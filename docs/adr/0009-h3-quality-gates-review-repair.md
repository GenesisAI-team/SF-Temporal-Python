# ADR-0009: Quality gates independientes, revisión separada y repair loops acotados (H3)

- **Estado:** Aceptado (GEN-52)
- **Contexto:** H2 (ADR-0008) deja la PR tras un único gate de tests re-ejecutado en sandbox y publica sin contrastar los criterios aprobados más allá del prompt del agente. El roadmap (H3) exige: ejecutar tests/checks reales en sandbox y recopilar evidencias; una revisión separada del agente implementador que contraste los criterios aprobados; detección de desvío de alcance (spec drift); y reparación acotada (máximo de intentos, límites de tiempo/coste) preservando idempotencia y auditoría. Sin merge automático.
- **Decisión:**
  - **Gates independientes (suite, no un solo comando).** `domain/quality.py:GateDefinition` + `default_gate_suite()` definen `tests` (`uv run pytest -q`), `lint` (`uv run ruff check .`) y `typecheck` (`uv run mypy src`), todo argv puro (sin shell). El adaptador `verification/quality_gates.py:SandboxQualityGatesRunner` (reemplaza al runner de un comando de H2) ejecuta la suite en un sandbox efímero: los gates corren independientemente entre sí (un gate fallido no impide los demás), pero los pasos de un gate se detienen en su primer fallo (los siguientes dependen de los anteriores). Cada gate produce un `GateOutcome` con comandos y evidencia (colas de salida); el agregado falla con `VERIFICATION_FAILED` (vocabulario estable de H2) listando los gates fallidos, y cada gate lleva `GATE_FAILED`.
  - **Revisión separada del implementador.** Port nuevo `review/ports.py:IndependentReviewer`; el adaptador real `review/sandbox.py:SandboxReviewer` abre SU PROPIA sesión/sandbox (nunca la del agente implementador) con el prompt determinista `build_reviewer_prompt`, que exige el formato estricto: `APPROVED` (línea exacta) o líneas `DEFECT: <detalle>` / `SPEC_DRIFT: <detalle>`. El parseo es regla pura (`parse_review_reply`): hallazgos > veredicto (fail-closed), sin veredicto → `REVIEW_FAILED` (no reparable), solo defectos → `REVIEW_REJECTED` (reparable), cualquier drift → `SPEC_DRIFT` (precedencia sobre los defectos).
  - **Spec drift bloquea sin reparar.** Si la revisión reporta cualquier `SPEC_DRIFT`, el workflow termina en `BLOCKED` con ese código y NO abre el repair loop: un cambio fuera de alcance no se arregla reimplementando; exige reaprobación humana de la spec (nueva `spec_version` ⇒ nuevo run key).
  - **Repair loop acotado.** Tras fallo de gates o `REVIEW_REJECTED`, el workflow entra en `REPAIRING` y re-ejecuta al agente (misma lógica de sesión; el prompt lleva `defects`, el feedback de gates/revisión) y repite gates → revisión. Presupuesto: `IssueWorkflowInput.max_repair_attempts` (settings `SF_FACTORY_REPAIR_ATTEMPTS`, 2 por defecto; 0 = sin reparación) contado sobre el MISMO `run_key` (el presupuesto de runs por issue no cambia). Límites de tiempo: timeouts por fase (agente 30 min, gates 15 min, revisión 10 min); límites de coste: un sandbox efímero por sesión. Agotado el presupuesto → `BLOCKED` con `REPAIR_BUDGET_EXHAUSTED` y el último fallo adjunto; si el agente falla durante la reparación → `AGENT_FAILED`. El bucle siempre termina: cada iteración consume un intento o retorna.
  - **Idempotencia y auditoría.** La línea de auditoría de reparación lleva id sintético `delivery#run_key#REPAIRING#<n>` (único por intento; los reintentos técnicos nunca duplican); el memo avanza a `REPAIRING` con el número de intento; el libro de runs no cambia (las reparaciones reutilizan el run reservado). La evidencia verificada viaja de extremo a extremo: `VerificationOutcome.gates` → resúmenes (`summarize_gate`) → contexto de la revisión y cuerpo del PR (`## Verified evidence`).
  - **Estados.** `VERIFYING` pasa a significar «gates superados» y `REVIEWING` «revisión independiente aprobada» (auditados antes de publicar; en H2 `REVIEWING` se auditaba tras publicar). El enum de estados congelado no cambia.
- **Consecuencias:** los tests de H2 que bloqueaban directamente por fallo de verificación pasan al presupuesto de reparación; el humo de integración inyecta un revisor simulado explícito. La revisión REAL exige imagen sandbox con el CLI del revisor: como en H2, sin ella la fase falla honesta (`REVIEW_FAILED`) — nada simulado. Sin merge automático: la PR sigue exigiendo revisión y merge humanos.
